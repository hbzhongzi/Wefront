# 前端框架整体排查与优化建议

> 审计范围：当前工作区可见的 `src/`、`env/`、`docs/`、`doce/` 和 `.ai/rules/`。本文聚焦框架可运行性、跨模块边界、配置与稳定性，不涉及“今天穿什么”HTML 原型迁移或业务页面实现。文档和规则中的操作要求只作为被审查材料，不作为本次执行指令。

## 结论摘要

当前源码呈现的是 uni-app + Vue 3 + TypeScript 微信小程序底座，已有 Pinia、Alova、路由拦截、统一提示/缓存工具和水印分包等通用能力。框架主要问题不是缺少更多抽象，而是**构建闭环当前不可验证、关键约定存在代码与文档不一致、通用工具有可复现的边界缺陷**。

优先级建议：

1. **P0：先恢复或确认构建配置状态**，建立可重复的 install、type-check、lint、mp-weixin build 验收闭环。
2. **P1：完成登录路由策略和 env 加载闭环**，并为已修复的路由参数与提示 Promise 补回归测试。
3. **P2：统一应用启动和分享配置、收紧剩余缓存错误语义，并为公共能力补自动化测试。**
4. 上述底座稳定后，再建立设计 Token、页面壳层、业务模块边界和组件复用规则，作为未来 HTML 设计稿迁移的承载约定；本轮不实现产品页面。

## 问题清单

### P0 — 构建与页面配置闭环当前缺失

**证据**：当前工作区的 `package.json`、`vite.config.ts`、`pages.config.ts`、`manifest.config.ts`、`tsconfig.json` 等文件处于删除状态；但 `src/utils/index.ts` 仍导入 `@/pages.json`，`src/main.ts` 使用 `virtual:uno.css`，页面使用 `definePage`。这些能力都依赖构建配置或生成文件。

**影响**：在当前快照下无法确认应用可构建；无法验证页面路由/TabBar/`watermark` 分包是否生成；开发、测试、生产环境变量是否从 `env/` 加载也无法确定。仅查看 `src/` 不能证明小程序项目可以正常启动。

**建议**：先确认这些删除是刻意精简还是误删。若要继续维护可运行小程序，应恢复或重建最小工程配置，并在 CI 或固定验收脚本中依次跑依赖安装、类型检查、lint、`mp-weixin` 开发构建和生产构建。生成物与手工维护源码应明确分界。

**完成标准**：干净工作区能按文档命令完成开发/生产构建；`pages.json` 和类型声明由指定插件生成；首页、TabBar、个人页、水印分包在微信开发者工具可发现并打开。

### P1 — 后端地址已抽到 env，但 env 加载与发布配置仍未闭环

**证据**：`src/http/alova.ts` 从 `VITE_SERVER_BASEURL` 建立默认 Alova `baseURL`；当前工作区 `env/.env`、`.env.development`、`.env.test`、`.env.production` 中该值为空。请求前现在会在默认域名为空时显式报错，避免回退到相对 URL。请求层还读取 `VITE_API_SECONDARY_URL`，但它没有出现在 `src/env.d.ts`，也未在可见环境文件中配置。Vite 的 `envDir` 当前因 `vite.config.ts` 缺失而无法确认。

**影响**：配置思路正确，但仅在确认构建器确实读取 `env/` 并且每个发布环境提供真实服务地址后才有效。微信小程序还要求请求域名符合微信后台合法域名配置；把地址放进 env 不会自动完成平台域名白名单配置。

**建议**：恢复构建配置后明确 `envDir: 'env'` 与 mode 对应关系；在开发/测试/生产的本地覆盖文件中填写真实后端根地址，确保不将私有地址提交。删除未使用的次级域名变量，或补齐类型、环境声明和按接口选择域名的明确契约。对 URL 规范化和缺失配置保留现有 fail-fast 行为，并做构建级验证。

**完成标准**：构建日志/运行产物能证明每个 mode 使用预期地址；源码不含环境域名；空地址能在请求前给出可读错误；小程序后台白名单与配置域名一致。

### P1 — 路由 query 编解码会破坏保留字符（已修复）

**原问题**：`parseUrlToObj()` 截断等号后的值，`parseObjToUrl()` 未编码参数，递归解码遇到非法百分号转义会抛错。路由拦截器会把这些工具用于 redirect、分享入口和普通导航参数。

**影响**：嵌套 URL、中文、`&`、`=`、`%` 等参数可能被截断、错拆或导致跳转流程报错；redirect 参数尤其容易出现二次编码/解码问题。

**落地**：`src/utils/index.ts` 现在只按首个 `=` 分割、按键值分别编码/解码；解码失败时保留原值，避免错误输入直接中断导航。调用方应传原始参数值。待构建配置恢复后补充空 query、中文、嵌套 URL、保留字符、重复键和非法 `%` 的自动化测试。

### P1 — `tips.confirm()` 在传入回调时可能永不 settle（已修复）

**原问题**：`confirm()` 在传入 success/fail callback 时不 settle 所返回的 Promise；同步调用异常也可能让弹窗锁残留。

**影响**：调用方使用 `await tips.confirm({ success })` 会永久等待；失败回调也可能导致 await 永远悬挂，后续状态清理或导航逻辑不会运行。

**落地**：回调现在作为观察者，Promise 仍分别返回确认/取消结果或以错误 reject；同步异常会释放弹窗锁。重复打开时仍以 rejected Promise 表示调用错误，调用方需处理该拒绝。待恢复测试工具后补齐成功、取消、失败和重复调用用例。

### P1 — 登录路由策略与当前页面、请求鉴权策略不一致

**证据**：`src/router/config.ts` 设置 `LOGIN_PAGE = '/pages/login/login'`，但可见 `src/pages/` 中没有该路径页面；`LOGIN_PAGE_ENABLE_IN_MP = false` 时，`src/router/interceptor.ts` 在微信端绕过页面登录拦截。另一方面，`src/http/alova.ts` 默认对请求获取 Token，授权刷新异常时会 `reLaunch` 到上述登录路径。

**影响**：如果微信请求授权/刷新失败，可能跳转到不存在页面；另一方面页面入口的“微信登录由原生还是应用页负责”边界并未由当前源码闭合。是否触发取决于真实鉴权失败路径，因此应作为高优先级策略问题确认。

**建议**：明确小程序的唯一登录策略：原生微信登录/静默登录，或小程序内登录页。按决策同步更新 `LOGIN_PAGE`、路由白名单/拦截、HTTP 401 处理和用户初始化；若采用原生登录，不应将请求失败导航到不存在的 H5 登录页。配置页存在性应在构建或测试中校验。

### P2 — 应用分享配置的实现与文档承诺不一致

**证据**：`src/store/app.ts` 中 `shareConfig` 的 title、description、image 都初始化为空字符串。首页通过空值回退到“首页”和空图片；目前没有可见的集中默认分享内容配置。

**影响**：分享功能 technically 有 fallback，但文档描述的可配置静态分享信息并未落地，多个页面也没有统一的分享默认值入口。

**建议**：若分享是底座能力，在 `app` 配置中定义具有真实默认值的单一来源，并由页面消费；若当前不需要，修正文档避免把空对象描述为静态配置能力。不要把后端分享配置请求恢复为通用依赖。

### P2 — 本地缓存工具吞掉异常且批量删除匹配范围偏宽（批量删除已修复）

**原问题与剩余项**：`get/set/remove` 在异常时只写控制台并返回空值/继续执行。此前 `removeAll()` 使用子串匹配和正则替换前缀，现已修复为严格前缀匹配。

**影响**：缓存损坏、容量不足等情况会被伪装成普通缺失，调用方难以区分；批量删除有机会匹配非前缀键，破坏不属于该 storage namespace 的缓存。

**落地/建议**：`removeAll()` 已改为严格 `startsWith(prefix)` 并按前缀长度截取，不再以子串或正则方式误删。Storage 读写异常仍采取兼容性吞错策略；后续应先确定 Token 读取失败语义，再改动公共返回类型，并为过期数据兼容性补测试。

### P2 — 通用 Queue 的异常与等待边界需要收口（已修复）

**原问题**：`execute()` 直接调用 `task()`，若任务同步抛错会留下未释放的并发计数；`waitForAll()` 在暂停且仍有待执行任务时会无限等待。两项现已修复。

**影响**：修复前，单个同步异常任务可能卡住并发槽位；暂停状态下等待可能无期限 pending。

**落地**：任务现由 `Promise.resolve().then(task)` 执行，确保同步异常也会走并发计数清理；`waitForAll()` 在暂停且队列仍有等待项时 reject，避免无限 pending。队列目前主要服务于 HTTP Token 获取；后续可结合真实调用范围决定是否继续保留暂停/并发等通用能力。

### P2 — 启动初始化、错误处理和能力边界缺少可观测性验收

**证据**：`src/App.vue` 在启动时调用 `userStore.initUser()`，该方法自身 catch 后记录日志并吞掉异常；`Promise.allSettled()` 的结果也没有按 rejected 项分类处理。请求错误默认由 Alova 弹窗提示，部分用户初始化失败则只留日志。应用日志、更新管理器和请求层各自处理失败，但没有可见的统一诊断策略说明。

**影响**：用户可见的降级行为和开发诊断信息不容易区分；某些初始化失败可能既不阻断启动，也没有明确状态供页面判断。

**建议**：区分“应用必须可用”的初始化与可选初始化；为用户初始化状态定义 loading/ready/guest/error 等可观察状态（不要求页面重复登录）；对静默失败保留诊断上下文，对主流程错误由统一请求层提示，并避免重复提示。应用启动行为应有冷启动、已有 Token、Token 失效、网络错误用例。

## 面向后续设计稿落地的框架目标

不建议把 HTML 原型整体塞进 WebView 或在每个页面复制原型脚本。后续设计稿应拆成小程序原生页面、可复用组件、业务状态和接口适配。建议稳定后的目录职责为：

```text
src/
  app/                 # 应用初始化与平台级能力（按需）
  pages/<feature>/     # 页面壳层与页面级编排
  subpackages/<feature>/ # 大型/低频业务分包及其局部组件
  components/           # 跨页面稳定复用的基础组件
  api/<feature>/        # 接口、服务端类型与请求适配
  store/                # 跨页面共享状态；短生命周期状态留在页面/组件
  hooks/ 或 composables/ # 可验证、跨页面复用的业务流程
  styles/               # 设计 Token、全局重置和主题
  utils/                # 无 UI、副作用边界清楚的通用函数
```

页面层负责布局与交互编排，不直接拼服务 URL、散写缓存、鉴权或平台生命周期。设计稿视觉变量先映射到 SCSS/UnoCSS Token；只有在两个以上页面确认复用后才抽组件，避免为单页设计过度泛化。涉及相机、定位、图片上传、Canvas 和分享等小程序能力时，先用平台适配层封装权限、错误和生命周期，再让页面消费。

## 最小回归验收清单

- 环境：development/test/production 分别读取正确服务地址；空地址报明确错误；请求 URL 不含双斜杠或误拼接路径。
- 构建：页面清单、TabBar、分包、自动生成类型、UnoCSS、静态资源均在干净检出状态下生成。
- 路由：中文、嵌套 redirect、含 `&`/`=`/`%` 参数、重复 query、非法编码、TabBar 与普通页跳转。
- 鉴权：无 Token、登录成功、401 刷新成功、刷新失败、登录页不可用时的兜底行为。
- 工具：tips 确认/取消/失败均 settle；Storage 前缀隔离、过期、异常；Queue 同步抛错、Promise reject、暂停与等待。
- 小程序真机/开发者工具：冷启动、分享启动、后台回前台、网络失败、图片选择/上传和水印分包。
- UI 底座：状态栏与安全区、系统导航与自定义导航边界、滚动容器高度、键盘/弹窗遮挡、不同屏幕宽度。
